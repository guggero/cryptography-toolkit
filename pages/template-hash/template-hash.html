BIP-446: Template Hash explorer

Explanation

BIP 446 proposes a new tapscript op code, OP_TEMPLATEHASH, that pushes a hash of the transaction that spends an output onto the stack. A script can compare that hash with a fixed value, or check a signature over it, and so restrict what the spending transaction looks like.

The interesting part is what the hash leaves out. It commits to the version, the lock time, the sequence numbers of all inputs, all outputs, the index of the input and its annex. It does not commit to the outputs being spent: neither which ones, nor their value, nor their script. A normal signature commits to all of those.

On this page you can edit a transaction and see which changes move the template hash. An output is locked to the transaction with the script OP_TEMPLATEHASH <hash> OP_EQUAL, and every edit is checked by really spending that output with the script engine of btcd.

Leaving out the spent outputs also has a price: see the security trade-offs at the end of the page.

The op code is a proposal and not active on any Bitcoin network.

Because the spent outputs are left out, the number of inputs is only committed to through their sequence numbers: adding an input changes sha_sequences.

Security trade-offs

Leaving out the spent outputs is what makes the template hash useful, and it is also where its risks are:

  • Every output with the same script can be spent by the same transaction. The script only holds the hash, but once the transaction is published, anybody knows it. If anyone pays to the address of a locked output a second time, anybody can publish the same transaction again with only the outpoint changed. No key is needed, and the outputs are paid a second time. Try it above: change the transaction ID or the index of the spent output, and the spend stays valid. A locked address must never be used to receive, and every output should get its own script.
  • The values of the spent outputs are not covered. If a spent output holds more than planned, the difference goes to the miner as fee (see Fee above). If it holds less, the transaction is not valid at all. BIP 446 leaves out the amounts partly so that such a mistake can be fixed: if the committed transaction has more than one input, a new coin of the right value can be spent alongside the stuck one. Adding an input does not help, it changes the template hash. With a single input and no other way to spend the output, the coins are stuck for good.
  • The same goes for signatures over the template hash. A signature checked with OP_CHECKSIGFROMSTACK against the template hash is rebindable: it is valid for every output with the same key and script. Since that opcode verifies a signature over any 32 bytes, a key that ever signs a message somebody else chose can be tricked into signing a template hash. A normal signature covers the outpoints, values and scripts of what it spends, so with normal signatures reusing a key or an address only costs privacy. With rebindable signatures it can authorize spending. See the rebindable signature scenario for both attacks, checked by the script engine.
